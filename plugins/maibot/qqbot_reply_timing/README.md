# QQBot 回复分段、等待与引用

## 分段

四个账号的群聊和私聊使用同一套分段规则。正文 80 字符以内整条发送。更长的正文优先在空行分隔的自然段之间拆，同一段内只在完整句末考虑拆分。逗号、空格和单个换行保留在同一条里。拆分时每条至少 36 字符、总共最多三条，短尾句并回上一条。列表、代码块和带附件的回复整条发送。

首段由原生 `reply` 发送，收到成功回执并确认首段已入库后，才通过框架发送接口逐条发剩余段落。发送失败或回执未知时结束本次分段。修改分段或出站链后，在隔离运行目录执行仓库根目录的 `pytests/test_qqbot_short_reply.py`，核对正文、条数、引用、附件、发送时间及失败处理。

## 等待与路由

通过公开接收、Replyer 和发送 Hook 记录本轮处理时间。发送时首条补等为 `max(0, 第一段原打字等待 - 本轮已处理时间)`。原等待按第一段文字计算，已耗时从接收本轮消息算到首段准备发送。后续分段及研究补充保持各段原有速度。

复制 `config.example.toml` 为本机 `config.toml`，设置 `plugin.enabled = true`，然后重启。发送速度继续读取 `response_post_process.typing_speed`。

原生后处理完成的文本段通过 `send_service.after_build_message` 进入统一打字计时，包括原生默认 `typing=false` 的首段。后续研究答复的首段也按普通续条等待，不会重新取得抵扣资格；没有预处理正文的插件通知保留其发送参数。

发送前若本账号 QQ 消息缺少 scope，通过 `config.get_plugin` 读取 NapCat 的 `napcat_server.connection_id` 补齐路由。先核对发送者为本实例机器人、已有账号字段一致；已有 scope、其他账号及非 QQ 消息不改。目标群/用户、附件、引用和正文原样透传，最终仍由原生发送器处理回执、存储和历史同步。

首条以 Replyer 的实际目标及其同一发送者在上下文中的最新消息计时。群聊里同一发送者补充可以提前结束旧首段的打字等待，再由 [`cpa_session`](../cpa_session/README.md) 核对回复是否过期并重新排队。并发发送只允许一条抵扣，明确失败释放资格。

## 引用

群聊和私聊都在首段实际发送前检查引用。实际回复的目标消息至少已有 30 秒，且同一会话里在它之后已有超过 5 条消息时，首段引用这条目标消息。其余情况直接发送。目标或消息数无法核对时也直接发送。后续分段沿用原有的不引用行为。
